# testing-strategy 来源能力档案

## Problem

在现代软件交付生命周期中，开发团队往往陷入两种极端测试误区：要么过度依赖厚重的端到端（E2E）测试导致流水线耗时极长、偶发脆弱失败（flaky tests）且维护成本高昂；要么仅编写大量微观单元测试却对关键集成点、跨服务契约及端到端故障盲视。此外，面对不同组件类型（如 API、数据管道、前端、基础设施），缺乏针对性的测试架构分层与覆盖策略，难以在测试覆盖率（coverage）、执行速度（speed）和维护开销（maintenance）之间取得平衡。

## When to Use

- **系统性测试架构设计（主要场景）**：当系统引入新特性、服务重构或进行技术架构演进，需要确定“我们应该如何测试”（how should we test）时。
- **编制结构化测试计划（Test Plan）**：在迭代开发前编制分层测试计划，明确划分单元测试、集成测试、端到端测试与契约测试边界。
- **异构组件分类测试规划**：针对 API 接口、数据管道、前端用户界面或底层基础设施等不同组件形态定制分层验证方案。
- **识别现有测试盲区与缺口**：评估存量代码库的测试现状，找出核心业务路径、异常处理与安全边界上的测试盲区。

## When Not to Use

- **编写具体语言断言语法的微观编码**：如仅需编写一个具体的 Jest 或 pytest 断言函数时（应直接由单元测试或 TDD 技能承接）。
- **极简原型或一次性验证脚本**：临时探索性质的 PoC 验证，不需要制定正规的多层测试金字塔与维护计划。

## Role

测试架构规划师与策略顾问（Test Architecture & Strategy Consultant）。专注于在系统层面权衡测试信心与执行成本，依据经典的测试金字塔原则为不同架构层级制定最经济、高置信度的测试覆盖与质量防护体系。

## Inputs

- **待测目标规格（Target Specification）**：拟测试的系统架构图、服务形态、技术栈及功能边界。
- **组件分类（Component Types）**：包括 API 端点、数据管道（ETL/Stream）、前端界面或基础设施资源。
- **质量与性能目标（Quality Targets）**：覆盖率指标、流水线时延约束、高可用及容灾要求。
- **现有测试套件基线**：当前存量测试覆盖范围及已知痛点。

## Outputs

1. **多维测试计划（Structured Test Plan）**：
   - 待测区域与业务关键路径清单。
   - 针对各区域分配的测试类型（单元/集成/E2E/契约/性能/混沌）。
   - 具体覆盖率量化目标与基线指标。
   - 典型代表性测试用例示例（Example Test Cases）。
2. **测试金字塔分层比例设计**：明确底层大量快速单元测试、中间层适量集成测试与顶层少量高置信度 E2E 测试的比例。
3. **测试覆盖缺口分析报告（Coverage Gap Analysis）**：指出遗漏的边缘用例、安全边界及数据一致性隐患。

## Workflow

1. **分析待测架构与组件类型（Analyze Architecture & Components）**：
   - 识别组件归属分类：API 端点、数据管道、前端交互或基础设施。
2. **应用测试金字塔构建分层组合（Apply Testing Pyramid）**：
   - 规划底层单元测试（Unit Tests）：大量、快速、聚焦于核心纯业务逻辑。
   - 规划中间层集成测试（Integration Tests）：适量、中速、覆盖 HTTP 交互与数据持久层。
   - 规划顶层 E2E 测试（E2E Tests）：少量、较慢、聚焦全链路关键路径的高置信度验证。
3. **按组件类型定制测试重点（Tailor Strategy by Component Type）**：
   - **API 端点**：业务逻辑编写单元测试；HTTP 网络传输与序列化编写集成测试；跨团队消费场景编写契约测试（Contract Tests）。
   - **数据管道**：重点覆盖输入校验（Input Validation）、转换正确性（Transformation Correctness）与幂等性验证（Idempotency Tests）。
   - **前端工程**：规划组件测试（Component Tests）、交互测试（Interaction Tests）、视觉回归（Visual Regression）及无障碍访问（Accessibility）。
   - **基础设施**：部署冒烟测试（Smoke Tests）、混沌工程（Chaos Engineering）与负载压测（Load Tests）。
4. **圈定测试边界与优先级（Define Coverage Priorities）**：
   - **重点覆盖（Focus On）**：商业关键路径（Business-critical paths）、异常与降级分支（Error handling）、极端边界情况（Edge cases）、安全边界（Security boundaries）、数据完整性（Data integrity）。
   - **显式跳过（Skip）**：琐碎的 getter/setter 方法、第三方框架内置代码、一次性探索脚本。
5. **输出测试计划并标记缺口（Generate Plan & Highlight Gaps）**：
   - 汇总生成清晰的测试策略与实施计划，附带示例用例，并标记出存量缺口。

## Branches

- **数据密集型分支（Data Pipeline Branch）**：重心落在数据转换的数学正确性、异常脏数据清洗与重复投递下的幂等处理。
- **UI 交互密集型分支（Frontend UX Branch）**：重心转向组件状态渲染、跨设备无障碍访问（a11y）与视觉回归比对。
- **分布式服务分支（Distributed API Branch）**：强化客户端消费契约（Contract Testing）、网络分区重试策略与熔断降级验证。

## Rules

- **金字塔成本倒逼原则**：越靠上的测试层（E2E）执行越慢、排查成本越高，严禁倒置金字塔（反模式：冰淇淋甜筒模型）。
- **价值导向覆盖原则**：仅聚焦高商业价值、高风险、异常与安全边界路径；坚决避免在没有业务价值的胶水代码和框架脚手架上刷覆盖率。
- **组件针对性原则**：不同形态的软件资产必须采用适配其故障特征的测试手段，禁止对数据管道使用前端组件测试思维，或对纯基础设施编写纯算法单元测试。

## Exceptions

- **超高安全性/金融级系统**：在资金交易结算核心链路中，可放宽 E2E 测试的比例限制，强制要求多重全链路影子测试与双写比对。
- **极早期 MVP 验证**：在原型阶段可优先编写精炼的冒烟集成测试，以最小代价覆盖主流程，后期再补齐底层金字塔。

## Dependencies

- **系统设计与架构规范**：系统模块切分、数据流向图与对外暴露接口契约。
- **测试框架与基础设施支撑**：各层级测试运行环境（如 Jest/Vitest/Playwright/Pytest/Postman 及 CI 流水线算力）。

## Permissions and Side Effects

- **权限要求**：只读分析权限，规划阶段无需生产或代码写入权限。
- **副作用**：生成的测试策略将直接指导开发和 QA 团队的测试套件搭建排期，影响 CI 流水线构建耗时与测试用例资产量。

## Gates

- **Gate 1: Pyramid Balance Gate**：评审规划的测试用例比例是否符合“大量快速单元、适量集成、极少关键 E2E”的金字塔结构，严禁端到端膨胀。
- **Gate 2: Component Alignment Gate**：核验是否为特定组件类型配置了核心防护（如数据管道必须包含幂等性测试，API 必须包含契约与业务逻辑分离）。
- **Gate 3: Critical Path Coverage Gate**：核查商业关键路径与安全边界是否均已建立可验证的测试用例目标。

## Open Questions

- 在微服务全面容器化和 Serverless 场景下，测试金字塔中间层（服务集成与契约测试）与本地 Mock / Stand-in 模拟的边界如何进一步自动化？
- 当大语言模型生成代码逐渐常态化时，自动化生成金字塔测试用例的保真度与维护成本平衡点如何确立？

## Unique Value

将复杂的测试决策系统化、结构化。在极简的抽象框架下，将抽象的“做好测试”拆解为可操作的测试金字塔比例、四类核心组件定制矩阵以及明确的价值剪枝标准，帮助工程团队在保障交付质量的同时大幅压降长周期测试维护包袱。
