# verification-before-completion 来源能力档案

## Problem

在复杂软件开发与智能体自主协作过程中，开发者或智能体极易滋生虚假成就感与惰性心理，在未经鲜活、完整命令验证的情况下，根据经验直觉、部分检查或静态臆测提前宣称“已完成”、“已修复”或“测试通过”。这种行为导致未定义函数、未捕获语法错误、偏离需求规格及隐性回归被推入主干甚至生产环境，彻底摧毁人机协同的信任基石。

## When to Use

- **宣称任何任务/阶段完成之前（强制）**：在口头或报告中做出“Done”、“已完成”、“功能就绪”等任何完成度断言前。
- **表达工作满意度或正向状态之前（强制）**：在发出“Great!”、“Perfect!”、“Looks good!”等评价前，必须先行调取证据。
- **提交代码（git commit）或创建拉取请求（PR）之前（强制）**：在生成任何持久化版本控制记录前必须执行完整门禁。
- **声明缺陷已修复之前（强制）**：必须针对原始复现路径执行端到端回归验证。
- **接收子智能体派发成果时（强制）**：必须独立核对版本控制差异（VCS diff）与运行输出，绝不轻信子智能体自报的“success”。
- **流转至下一个开发任务之前（强制）**：确认前序任务的所有验收指标均有当前会话内的最新运行输出背书。

## When Not to Use

- **早期纯头脑风暴与构思讨论**：在尚未编写具体实现、未产生可验证代码或产物的发散思考阶段。
- **正在逐步排查日志的探查过程中**：正在探索故障现象并连续执行中间命令，尚未得出结论或宣称结论前。

## Role

证据导向型质量仲裁员（Evidence-Driven Quality Arbiter），奉行“先出具鲜活证据，后发表状态断言”的绝对诚实守则。视未经验证的臆断为谎言，以无偏证据作为唯一裁决标尺。

## Inputs

- **待验证断言（Claim）**：例如“测试全量通过”、“编译无错”、“缺陷已根治”、“需求规格全覆盖”。
- **目标验证命令（Verification Command）**：能够绝对证明该断言真伪的可执行命令行指令（如 `pytest`、`npm test`、`cargo build`、`tsc --noEmit`）。
- **执行环境与最新产物**：当前工作树的最新代码变更、构建工件及测试套件。

## Outputs

鲜活证据驱动的验证报告与状态陈述（Evidence-Backed Status Statement）：
1. **完整命令执行日志**：包含完整的标准输出与错误输出，不得依赖历史缓存或部分截断。
2. **退出码与统计核验**：明确的 Exit Code（如 exit 0）以及零失败统计（如 `0 failed, 34 passed`）。
3. **真实状态断言**：
   - 验证通过：附带输出证据的成功声明（State claim WITH evidence）。
   - 验证失败：附带输出证据的客观现状说明（State actual status with evidence），严禁掩盖错误。

## Workflow

1. **识别验证命令（IDENTIFY）**：
   - 明确哪一条具体的完整命令能够无争议证明当前断言。
   - 禁止用轻量命令代替严苛命令（如禁止用 Linter 代替 Compiler）。
2. **执行新鲜完整命令（RUN）**：
   - 在当前消息交互中立即执行全量命令，确保不是引用上一次或历史运行结果。
3. **读取完整输出（READ）**：
   - 检查进程退出码（Exit code），逐行扫描报错信息，核实失败用例计数。
4. **比对核验结论（VERIFY）**：
   - 若输出与预期断言不符：如实陈述实际失败状态与具体日志，严禁提前宣布胜利。
   - 若输出完全证实断言：结合日志证据陈述验证通过。
5. **正式发表结论（ONLY THEN）**：
   - 仅在完成上述 4 步后，才允许向人类伙伴或工作流声明任务完成。跳过任何一步等同于欺瞒。

## Branches

- **验证完全通过（All Clear）**：命令退出码为 0，错误与失败计数均为 0，产出证据后推进到 commit/PR 或下一任务。
- **命令报错或断言失败（Verification Failed）**：拦截提交流程，陈述实际阻断日志，进入缺陷定位与修复流程。
- **回归测试验证分支（Red-Green Verification）**：
  - 编写新测试 -> 运行（必须失败/Red） -> 编写修复 -> 运行（必须通过/Green） -> 暂存恢复代码验证仍能失败 -> 最终确认测试有效性。
- **多智能体成果接收分支（Subagent Audit）**：
  - 接收到子智能体返回报告 -> 不信任其自报文字 -> 执行 `git diff` 审查改动 -> 运行独立测试验证 -> 确认实际完成状态。

## Rules

- **铁律（The Iron Law）**：`NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE`（无鲜活验证证据，严禁宣称完成）。
- **言行一致与神髓优先**：违反本规则的字面即是违反本规则的实质精神；换用同义词（如“看起来搞定了”、“大概没问题”）同样属于严重违规。
- **严禁提前宣泄情绪**：在命令执行完毕并阅读输出前，绝对禁止表达“Great!”、“Done!”、“Perfect!”等预先庆祝词句。
- **禁止推断与局部代全**：Linter 通过不等于编译通过；单测通过不等于需求全满足；前一次运行通过不等于当前改动后依然通过。
- **子智能体零信任**：绝不将子智能体的自称“成功”作为验收依据，必须由主控审查 VCS diff 并独立验证。

## Exceptions

- 无任何执行例外。无论开发者何等疲劳（"I'm tired"）、何等自信（"I'm confident"），一律严禁开例外通道（"No shortcuts, no exceptions"）。

## Dependencies

- **执行运行时环境**：能够直接执行项目构建、测试与静态类型检查的基础 CLI 环境（如 bash、python、pytest、node、npm 等）。
- **版本控制系统**：依赖 `git diff`、`git status` 审查物理文件变更。

## Permissions and Side Effects

- **权限要求**：只读与命令执行权限（运行构建、测试、代码比对命令）。无破坏性工作区清理权限。
- **副作用**：触发构建工件生成与测试套件执行，产生标准输出及日志。

## Gates

- **Gate 1: Pre-Claim Identification Gate**：在发表任何成功断言前，必须在提示上下文中已存在明确的验证命令及其真实返回。
- **Gate 2: Exit-Code & Zero-Failure Gate**：命令返回值必须为 0，且测试失败数与语法错误数必须明确确认为 0。
- **Gate 3: Subagent Diff Inspection Gate**：在采信子智能体交付成果前，必须执行 VCS diff 检查，确认修改真实存在且符合预期。

## Open Questions

- 当测试套件运行极其漫长（如端到端需要数小时）时，如何在“鲜活全量验证”与“快速渐进式反馈”之间建立标准的分级门禁机制？
- 在缺乏自动化测试套件的纯配置或基础设施项目中，如何固化等价于“命令退出码 0”的强物理证据？

## Unique Value

将软件工程中极易流于形式的“自觉性完成”重塑为具有强约束力的物理门禁协议。通过建立不可逾越的 5 步验证函数与反辩解表，彻底杜绝了大语言模型与工程师常见的幻觉完成、提前庆祝及跳步欺瞒，为自动化协同构筑了坚如磐石的可信赖质量底线。
