# test-driven-development Dossier

## Problem
在没有失败测试守护的情况下盲目编写生产代码，极易滋生不可靠的假设、缺失边界条件、过度设计以及隐藏缺陷。事后补写测试（Tests-after）往往沦为顺应已有实现的心理安慰，仅能回答“代码当前做了什么”而非“系统应当达成什么”，不仅极易遗漏关键用例，更无法证明测试自身是否真正具备捕获错误的能力。此外，滥用 Mock 测试桩、在生产类中混入测试专用方法、不完整的数据结构模拟等反模式，会导致“测试全绿但集成即崩溃”的虚假安全感。

## When to Use
1. 开发任何全新业务功能（New Features）时。
2. 修复任何系统缺陷（Bug Fixes）时，必须先编写能够稳定复现该缺陷的失败测试。
3. 重构现有代码库（Refactoring）与优化内部实现时。
4. 发生任何外部或内部行为变更（Behavior Changes）时。
5. 设计新 API 或组件接口，以调用者姿态推演期望用法时。

## When Not to Use
1. 纯一次性抛弃型原型探索（Throwaway Prototypes，且必须在探索完毕后彻底丢弃原型代码重新用 TDD 实现）。
2. 工具自动生成的机器代码（Generated Code，如 ORM 自动编译产物）。
3. 纯静态配置文件（Configuration Files，如简单的 JSON/YAML 参数字典）。
4. 无法通过任何外部输入输出进行行为验证的底层绝对不可控外部物理硬件驱动（需人工确认例外）。

## Role
严苛的敏捷软件工程教练与 TDD 实践专家（TDD Practitioner & Craft Lead），坚决奉行“铁律：无失败测试绝不写生产代码”，以红-绿-重构循环为唯一纪律，无情识别并根除一切事后补测借口与 Mock 反模式。

## Inputs
1. **Target Feature / Bug Report / 待实现功能或缺陷报告**：明确的行为描述、输入输出预期或缺陷复现线索。
2. **Existing Codebase & Test Suite / 现有代码库与测试套件**：项目的测试运行器配置（`npm test`, `pytest`, `vitest` 等）与被测系统上下文。
3. **Execution Context / 执行上下文**：是否处于全新开发、缺陷修复或重构阶段。

## Outputs
1. **Failing Test (RED) / 失败测试用例**：一个最小化、命名清晰、断言单一行为且调用真实代码的红测试。
2. **Minimal Passing Implementation (GREEN) / 最小化通过代码**：刚好足以使测试通过的最简代码实现，坚决剔除任何臆想的未来扩展（YAGNI）。
3. **Refactored Clean Code (REFACTOR) / 重构清洁代码**：在所有测试全绿的前提下消除重复、优化命名、提取辅助函数，绝不引入新行为。
4. **Pristine Test Run Evidence / 纯净的测试运行证据**：包含测试命令输出，无警告、无异常且用例全部通过。

## Workflow
1. **RED - Write Failing Test / 编写失败测试**：
   - 编写且仅编写一个最小化的测试用例，明确表达所期望的真实行为；
   - 测试必须命名清晰、断言单一、使用真实实现（除非极端不可避免否则严禁使用 Mock）。
2. **Verify RED - Watch It Fail / 见证失败（强制不可逾越）**：
   - 执行测试套件命令；
   - 确认测试失败（而非编译语法崩溃）；
   - 确认报错信息与预期相符，确认失败原因是由于功能缺失而非拼写或配置错误。
   - 若测试直接通过，说明在测已有逻辑或测试无效，必须修正测试。
3. **GREEN - Minimal Code / 编写最小代码**：
   - 编写足以使测试变绿的最简生产代码；
   - 坚决杜绝过度设计、预先泛化或添加测试未要求的任何参数。
4. **Verify GREEN - Watch It Pass / 见证通过（强制不可逾越）**：
   - 重新运行测试命令；
   - 确认当前测试通过，且整个项目的存量测试全部保持全绿；
   - 确认控制台输出纯净（无隐式告警）。
5. **REFACTOR - Clean Up / 保持绿灯下的清洁重构**：
   - 消除重复代码（DRY）；
   - 优化变量与函数命名；
   - 提取局部辅助函数；
   - 重构过程中保持测试始终全绿，严禁在此阶段塞入新功能。
6. **Repeat / 推进下一个微循环**：
   - 转向下一个特性的失败测试，往复循环直至需求全部满足。
7. **Verification Audit / 完工前符合性核验**：
   - 检查是否每一段生产代码均有失败先行的测试；
   - 检查测试是否均使用真实依赖，排查是否陷入 5 大 Mock 反模式。

## Branches
- **Branch A: Feature Development / 新特性开发循环**：从零编写测试 API 调用 -> 见证失败 -> 补齐最简逻辑 -> 绿灯 -> 重构。
- **Branch B: Bug Fix / 缺陷修复循环**：编写复现特定缺陷的回归测试 -> 见证测试因缺陷存在而失败 -> 修复生产代码 -> 见证测试通过 -> 固化防倒退门禁。
- **Branch C: Spike Exploration / 探针调研分支**：在设计完全不明确时允许编写非 TDD 试验代码，但探索完毕后必须彻底删除试验代码，从头依 TDD 重新落地。

## Rules
1. **铁律（The Iron Law）**：**没有失败测试，绝不写生产代码（NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST）**。一旦发现先写了代码，必须立刻删除并从零重来，严禁保留作为“参考”。
2. **必须亲眼见证失败（Verify RED）**：如果不亲眼看着测试失败，就无法证明它测试了正确的事情；立即通过的事后测试毫无证明价值。
3. **极简代码通过原则（Minimal Implementation）**：实现阶段只写能通过当前测试的最少代码，杜绝任何未被测试要求的参数、重构或超前设计（严格遵循 YAGNI）。
4. **单一断言与意图清晰**：每个测试专注验证一件事；名称中若包含 "and" 说明职责混合，必须拆分为多个测试用例。
5. **严禁测试 Mock 自身行为（Anti-Pattern 1）**：Mock 是隔离手段而非被测对象；严禁断言 `*-mock` 的存在或单纯检验 Mock 调用次数，必须测试真实组件行为。
6. **严禁生产类混入测试专用方法（Anti-Pattern 2）**：严禁在生产类中增加仅供测试清理使用的 `destroy()` 或特权状态方法，生命周期管理应交由测试工具函数（`test-utils`）处理。
7. **严禁不理解依赖链盲目 Mock（Anti-Pattern 3）**：严禁在未理解真实方法副作用（如写配置）的前提下盲目 Mock，避免破坏被测代码实际依赖的底层行为；必须在最底层实施最小化隔离。
8. **完整结构模拟守则（Anti-Pattern 4）**：若不得不 Mock 响应对象，必须完整镜像真实 API 的全量数据结构字段，严禁部分残缺模拟（Partial Mocks）掩盖下游取值崩溃。
9. **测试即实现的一部分（Anti-Pattern 5）**：严禁在未编写测试的情况下宣称“代码已完成，等待测试”，测试缺失等同于实现未完成。

## Exceptions
1. **人工显式许可**：仅在获得人类协作者明确许可的极少数边界（如纯抛弃型探索、自动生成代码、无逻辑纯文本配置）下允许豁免 TDD。
2. **外部不可控依赖**：对于真实付费第三方支付接口、短信用量消耗等高成本外部服务，允许在系统架构边界处采用行为对齐的高保真 Stub，但本地逻辑必须真实执行。

## Dependencies
- 单元测试与集成测试运行环境（如 Jest, Vitest, Pytest, Go testing）。
- 断言库与覆盖率统计工具。

## Permissions and Side Effects
- **只读操作**：检查现有测试套件、运行测试命令、分析报错堆栈与覆盖率。
- **本地代码修改**：创建或修改测试文件与生产代码文件，运行本地测试命令。
- **强制删除副作用**：在违背 TDD 先行铁律时，具备强制删除违规编写的生产代码之责任。

## Gates
- **G-Iron-Law-Compliance**：进入生产代码编辑前，必须已存在且已验证失败的测试用例。
- **G-Red-Verification**：必须有执行命令与确切预期的失败信息作为凭证（不能是语法异常）。
- **G-Green-Verification**：实现编写后必须全绿且输出干净（无 warning/error）。
- **G-Anti-Pattern-Audit**：自审排除 5 大 Mock 反模式（无 mock-assert、无生产类测试方法、无盲目 mock、无字段残缺 mock）。

## Open Questions
1. 在高并发分布式竞态条件与异步事件流调试中，如何通过纯 TDD 确定性复现毫秒级时序缺陷？
2. 针对复杂图形渲染与大模型自由文本生成，如何界定最小有效 TDD 断言粒度？

## Unique Value
树立了无懈可击的软件工程专业主义标杆，将测试驱动开发从一种“可选风格”升华为“不可违反的铁律”；通过极致严密的红-绿-重构循环、对借口借词的彻底封堵，以及对 Mock 滥用反模式的深度门禁防范，根本性杜绝软件腐化与回归隐患。
