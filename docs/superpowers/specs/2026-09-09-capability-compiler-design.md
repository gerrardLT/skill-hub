# Dev Loop 能力编译器设计规格

## 1. 目标

将项目内已下载的通用研发 Skills 作为只读原料，完整拆解其方法、规则、边界、模板、示例、工具动作和 Gate；通过可追溯的比较、取舍与实测，生成可独立调用、替换和组合的原子能力插槽，再由场景配方和 dev-loop 总控组成持续反馈闭环。

## 2. 已确认决策

1. 最终形态是“dev-loop 总控 + 独立原子插槽”。
2. `skills/` 是只读原始资产库；优化结果进入独立目录。
3. 插槽按可独立执行、可独立验收的能力划分，不按原 Skill 或固定数量划分。
4. 重复和冲突通过来源证据、质量规则和对照实测裁决，不能靠提示词顺序覆盖。
5. PostHog 永久排除。
6. 第一期不提纯平台专用能力；Sentry、Datadog、Azure、Vercel 和 Cloudflare 等只登记、隔离和保留。
7. 试点用于校准提纯方法，不缩减全量目标。
8. 未通过 Gate 的候选插槽和配方不得接入 dev-loop。

## 3. 不变量

- 不修改、移动或删除 `skills/` 内的原始文件。
- 目录存在和 `SKILL.md` 存在只证明文件落盘，不代表来源完整、依赖齐全或能力可运行。
- 来源版本无法核实时标记为未知，不能从本地哈希反推上游版本。
- 阅读脚本不等于授权执行脚本；不得在审计时自动安装依赖、调用生产服务或使用真实凭据。
- 所有原始有效内容必须映射到优化插槽或明确的取舍记录。
- 所有优化规则必须能回溯到来源，或明确标记为新增设计。
- 信息不足返回 `needs-input`，不得编造。
- QA 与实现职责分离；QA 只报告和回退，不修改产品代码自证通过。
- 硬性失败不能被总分抵消，包括捏造证据、越权操作、关键规则遗漏和 Gate 错误放行。
- Token、篇幅和速度是次级指标，不能以能力退化换取精简。

## 4. 总体架构

```text
skills/（只读原料与附件）
        ↓
资产清点与完整性核验
        ↓
语义拆解：方法 / 规则 / 边界 / 模板 / 示例 / 工具 / Gate
        ↓
跨 Skill 对齐：重复 / 互补 / 条件差异 / 冲突 / 强耦合
        ↓
证据取舍：保留 / 合并 / 改写 / 条件化 / 排除 / 待验证
        ↓
slots/（统一契约的原子能力）
        ↓
recipes/（顺序、数据传递、权限和 Gate）
        ↓
dev-loop（任务识别、编排、状态、证据和失败回流）
        ↓
真实运行与复盘反馈回评测、插槽和配方
```

平台专用能力进入隔离清单，不参与第一期的提纯和运行时组合。PostHog 不进入任何资产、插槽或配方。

## 5. 资产身份模型

必须区分以下概念：

- `catalog-entry`：原清单中的一个能力项，允许跨域重复。
- `source-package`：一个来源仓库或已下载套件。
- `skill-root`：包含 `SKILL.md` 的物理入口。
- `embedded-skill`：套件中的内嵌 Skill。
- `snapshot`：当前本地文件内容及其哈希。
- `duplicate-group`：内容相同或来源相同的副本关系。
- `capability-unit`：从来源中提取的最小完整语义单元。
- `slot`：通过 Gate 后发布的单一职责能力包。
- `recipe`：多个插槽的有序组合与数据传递规则。

“68 项能力”“顶层目录数”和“全树 `SKILL.md` 数”必须分别报告，不得混用。

## 6. 原始 Skill 拆解

每份纳入范围的 Skill 必须完整阅读入口及其可达附件，生成：

1. 整体 dossier：问题、适用场景、非适用场景、角色、输入、输出、完整流程、依赖、权限、副作用、验收和疑点。
2. 语义单元：来源位置、类型、原始含义、边界、依赖、候选去向和审计状态。
3. 阅读覆盖记录：入口章节、引用文件、脚本和未读取原因。

语义单元按完整行为拆分，不按段落机械切割。示例若承载正文未说明的边界，也必须作为有效内容提取。

## 7. 取舍模型

每个语义单元最终只能进入一种状态：

- `retain`：原样保留；
- `merge`：与其他内容合并；
- `rewrite`：保留行为和边界后改写；
- `conditionalize`：只在明确条件下启用；
- `exclude`：从优化版剔除，但原料仍保留；
- `defer`：证据不足或超出本期范围。

每条决策必须记录原文、理由、承接位置、潜在损失和验证案例。仅写“重复”“过时”或“质量差”不构成充分依据。

## 8. 原子插槽契约

每个插槽至少包含：

- 唯一 ID、名称、版本和职责；
- 触发条件、适用边界和非目标；
- 输入字段、必填条件和允许的未知值；
- 输出字段及语义；
- 执行方法和必要附件；
- 依赖、工具、权限和副作用；
- 禁止事项；
- `passed`、`failed`、`needs-input`、`blocked` 状态；
- 完成 Gate 和失败证据；
- 来源映射与评测版本。

“原子”表示职责单一且可独立验收，不要求把强耦合方法拆断。来源和完整评测记录保留在维护侧；运行时只加载执行所需内容。

## 9. 配方与总控边界

- 插槽负责具体方法。
- 配方负责插槽选择、顺序、输入输出映射、并发限制和 Gate。
- dev-loop 负责读取项目状态、选择配方、注入项目证据、执行插槽、保存产物、判断回退和记录决策。
- 多个插槽不得依赖提示词先后顺序争夺同一职责。
- 两个步骤写同一产物时默认串行；并行结果必须由显式汇总步骤合并。
- 上游输出变化后，依赖它的下游证据失效，必须重新验证。

## 10. 验证体系

### 10.1 来源覆盖

双向追踪：

- 原始有效内容 → 插槽或取舍记录；
- 插槽规则 → 原始来源或新增设计记录。

覆盖检查不能证明取舍正确，只能证明没有静默丢失或无来源新增。

### 10.2 能力对照

先冻结任务要求、硬失败和评价标准，再生成候选插槽。案例覆盖：正常、信息不足、边界、异常、不适用、冲突和工具不可用。

原始 Skill 不是标准答案。基线与候选必须在相同模型、输入、工具权限和预算下比较。具有生成波动的案例重复运行。调优案例和留出案例分开；留出案例一旦参与调优就不再作为独立验收证据。

### 10.3 组合验证

验证字段语义、上下游传递、未知项保留、权限、重复执行、冲突、Gate 阻断、失败回流和插槽替换兼容性。

必须进行变异测试：故意删除关键约束、放宽 Gate 或破坏输出字段，相应测试必须变红。

### 10.4 人工评审

使用 skill-creator 的 `eval-viewer/generate_review.py` 展示匿名化对照输出和 benchmark。人工评审与自动断言共同构成证据，不能只看单一总分。

## 11. 发布 Gate

插槽或配方只有满足以下条件才能发布：

1. 来源和依赖已核实，或未解决缺口清楚且不影响发布范围；
2. 原始关键能力都有明确去向；
3. 输入、输出、边界、权限和失败语义完整；
4. 无未解决的阻断性冲突；
5. 调优、留出、变异和组合测试通过既定标准；
6. 硬性失败为零；
7. 人工评审已完成；
8. 原始 `skills/` 基线无变化。

## 12. 实施顺序

1. 冻结原始资产基线与范围。
2. 建立全量资产底账和缺口报告。
3. 全量拆解纳入范围的 Skills。
4. 构建跨域能力地图和依赖图。
5. 以“需求到验收标准”能力簇完成提纯试点。
6. 按校准后的方法逐簇完成通用能力提纯。
7. 构建配方并执行组合与闭环验证。
8. 将通过 Gate 的插槽和配方接入 dev-loop，完成全量终验。

每一阶段的 Gate 未通过时在当前阶段补齐，或回退到造成缺口的上游阶段；不得带病推进。
