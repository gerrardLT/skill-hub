## 一、做了什么

把 154 项能力合并为 68 项，并补齐了上一轮遗留的三类缺陷。

### 1. 换行与哈希断层（已修复）

上一轮合并时 Windows 文本模式把 LF 写成了 CRLF，导致 30 项「未改动」的 Skill 内容虽相同但哈希全变，与既有溯源链、冻结清单、评测记录全部对不上。

现在编译器统一以 `newline='\n'` 写出：

| 检查 | 结果 |
|---|---|
| 30 项 1:1 Skill 与源文件字节一致 | **30 / 30** |
| 含 CRLF 的文件 | **0** |
| 索引哈希与实际文件不符 | **0** |

溯源记录新增 `source_skill_sha256`，逐项绑定每个来源 Skill 的原始哈希。

### 2. 拼接文档结构（已重构）

上一轮 38 份合并文档是原文档直接串联，出现多个 H1，最长一份 51 KB，模型无法判断该用哪套流程。

现在每份合并文档：

- **只有 1 个 H1**，内层标题统一降两级，层级清晰；
- 顶部有 **Mode selection 表**，列出每个模式、**该模式自己的权限**、适用场景、以及该路由到别处的情况；
- 执行器新增 `select_mode()`，运行时只装载被选中的那一个模式，不再把整篇灌进提示词。

结构自检：**0 问题**。

### 3. 权限语义（发现并修复了严重缺陷）

这是本轮最重要的发现。

上一轮我用「取来源中最常见的权限」作为合并后的权限。检查 154 条来源→目标映射后发现：

- **0 项越权**（没有放宽权限，fail-closed 未被破坏）；
- **9 项被过度收窄**，即某些模式在合并后的权限下**根本无法完成其契约工作**。例如：
  - `cloud-and-edge-application-deployment` 合并后为 `workspace-write`，但其中 3 个模式原本是 `remote-write-authorized-only` —— 这些部署模式再也无法真正部署；
  - `tool-and-runtime-bootstrap` 合并后为 `local-exec`，但包含需要 `local-system-write` 与 `workspace-write` 的模式；
  - `root-cause-investigation` 合并后为 `external-read`，而原能力是 `workspace-write-local-exec`。

**严格按权限分组合并会得到 99 项，不是 68 项。** 要保住 68 这个数字，只能让权限边界保持可见。

采用的修复：

- 契约新增 `mode_permissions: {模式 → 权限}`，每个模式保留自己原本的权限身份；
- 文档级 `permission_identity` 仅作默认值，且明确标注「运行时以所选模式的权限为准，绝不用文档里最宽的那个」；
- 执行器新增 `resolve_permission()`，按所选模式解析生效权限，并写入执行证据。

验证：**154 条映射权限检查，0 处不符，0 处越权。**

## 三、审核过程中的修复

审核不是走过场。首轮 27 项中 **17 项被拒**，全部由 deepseek 指出真实缺陷，例如：

- 题面里的到期日 **2026-03-15 已过期**（当时是 2026-05-09），却要求产出有效的配对身份；
- 题面声明「续期日等于提交日合法」，而内联的失败测试却断言相等应报错 —— **自相矛盾**；
- 契约要求的输出（如 `dry-run and validation evidence`）没有任何 rubric 覆盖；
- 题面要求说明假设与未决项，rubric 却不检查。

修复方式是自动化的「修复—复审」循环（最多 5 轮），每轮都把**被拒版本完整保留**在 `curation/v2/optimization-1.1.0/consolidated-68-*-revision-N-rejected.json`，从不覆盖。

收敛过程：`17 拒 → 19 拒 → 8 拒 → 3 拒 → 1 拒 → 0 拒`。

## 五、仍然存在的限制

必须说清楚，不要把这套东西当成已经可以无人值守跑完整项目：

1. **只评测了 38 项合并能力**。30 项 1:1 保留的能力内容与源文件字节一致，因此未重复评测 —— 它们的证据沿用 154 目录那一轮。
2. **只验证了能力级，没验证配方级**。评测是「给一个任务 + 一个能力文档 → 比两版输出」，没有跑完整的 15 阶段配方。
3. **端到端执行仍是 mock**。`recipe_execute.py` 能解析 V2 的 `skill_ref` / `dependency_records`，但真实跑通一条完整研发闭环用的是替身 worker，不是真实模型驱动多阶段。
4. **未发布**。`consolidated-68` 是隔离候选，`slots/v2/1.0.0` 与 `recipes/v2/1.0.0` 未被修改，正式发布仍需独立批准。
5. **本地模型的能力上限**。出题与审核都用 flash 级模型，题目复杂度受其限制；这轮证明的是「合并不劣化」，不是「能力达到工业上限」。
6. **13 项出现 loss**。虽然统计上不超过随机波动，但每一项的具体原因值得后续抽查，尤其是 `design-context-and-direction-contract`（2 负）与 `isolated-task-implementation`（2 负）。
